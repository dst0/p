# 2026-08-25 — Benchmark candidate registry strictly increasing gaps

- **Status:** Resolved
- **Task/context:** Registering immutable candidate version and runtime bindings during paired project-instruction benchmark execution in `benchmarks/src/harness/candidate-registry.ts`.
- **Unexpected observation or failure:** When running a benchmark candidate after prior intermediate candidate iterations failed before valid registration (e.g., persisted registry ended at `5.0.1-rc.10` while running `5.0.1-rc.14`), the benchmark launcher failed pre-provider during initialization with `Error: Benchmark next candidate must be 5.0.1-rc.11`.
- **Evidence:** The registry enforced strict contiguity (`candidateNumber(version) === index + 1` during read/validation and `candidate === 5.0.1-rc.${candidates.length + 1}` during registration). When source iterations rc.11-rc.13 failed before completing valid registration, launching rc.14 was rejected because the registry expected the exact next integer rc.11. Forcing contiguous candidate registration would corrupt provenance by requiring fabricated candidate runs or relabeling later source code to match missing sequential numbers.
- **Approaches tried:**
  - **Attempt:** Enforce strictly contiguous candidate registration from `rc.1` without skips.
    - **Outcome:** Did not work
    - **Why:** In real development workflows, intermediate candidate runs may fail or be aborted before registration, or candidates may be bumped during rapid iteration. Strict contiguity forces fabricated benchmark candidate records or relabeling subsequent source commits, corrupting candidate runtime provenance.
  - **Attempt:** Allow positive candidate versions to have numeric gaps as long as persisted and newly registered candidate versions are strictly increasing, while preserving idempotency for exact candidate reruns on the same runtime and rejecting rollbacks, older candidates, and duplicate bindings.
    - **Outcome:** Worked
    - **Why:** Preserves immutable runtime provenance without requiring artificial sequential runs for aborted/failed intermediate iterations, while strictly preventing regressions, duplicate bindings, and non-increasing registry corruption.
- **Root cause:** Candidate registry validation and registration logic assumed unbroken sequential version progression (`index + 1` and `candidates.length + 1`), disallowing valid sparse iterations.
- **Resolution:** Modified `validateRegistry` in `benchmarks/src/harness/candidate-registry.ts` to require candidate versions to be strictly increasing (`candidateNumber(version) > candidateNumber(candidates[index - 1].candidateVersion)`). Modified `registerBenchmarkCandidate` to verify new candidate versions are numerically greater than the last registered candidate (`candidateNumber(candidate) > candidateNumber(lastCandidate.candidateVersion)`) instead of strictly contiguous. Added regression tests in `benchmarks/test/harness/candidate-registry.test.ts` for allowed gaps, initial gap registration, rollback rejection, and malformed non-increasing persisted states.
- **Verification:** Verified test failures in `benchmarks/test/harness/candidate-registry.test.ts` before implementation (3 failed tests: gap rejection, initial gap rejection, and malformed state error mismatch); verified test passes after implementation including authoritative rc.10→rc.15 sparse gap registration and idempotent rerun (7/7 tests pass); verified `benchmarks/test/harness/candidate-integration.test.ts` (5/5 tests pass); ran full benchmark test suite `npm run test:benchmarks` (312/312 tests pass); verified release audit tests `npm run test:release-audit` (61/61 tests pass); verified change fragment validation, `git diff --check`, and POSIX EOF formatting.
- **Prevention/follow-up:** Candidate registry tests now explicitly exercise allowed sparse numeric progressions including the authoritative rc.10→rc.15 regression sequence (registering rc.10 with FINGERPRINT_A, advancing with a subsequent gap to rc.15 with FINGERPRINT_B, idempotent rc.15 rerun, and asserting exact [rc.10/A, rc.15/B] persisted bindings), rollback rejections, and malformed out-of-order persisted state fixtures.
- **Reusable learning:** Version sequence gates that bind immutable artifact provenance should enforce strict monotonicity (strictly increasing order) rather than contiguity, preventing workflow deadlocks when intermediate versions fail or are skipped while still preventing rollbacks.
