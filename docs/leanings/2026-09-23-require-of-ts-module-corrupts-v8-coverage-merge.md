# 2026-09-23 — `require()` on a TS module inside a Vitest test corrupts cross-file v8 coverage merging

- **Status:** Resolved
- **Task/context:** Debugging why `packages/coding-agent`'s full `test:coverage` run reported `src/config/install-paths.ts` line 84 (`getSelfUpdateUnavailableInstruction`'s `bun-binary` branch, exercised by `test/bun-binary-update-instruction.test.ts`) as uncovered (`DA:84,0` in `coverage/lcov.info`), which failed the `scripts/check-changed-coverage.js` changed-line gate — even though running that single test file (alone, or via a small subset) always showed the line as covered, and the test itself passed in every full run.
- **Unexpected observation or failure:** Coverage for `getSelfUpdateUnavailableInstruction`/`getUpdateInstruction` in `install-paths.ts` flipped from covered to uncovered once the ordered test-file list crossed a specific size (109 files: covered; 110 files: uncovered), reproducing even with a single forked worker process (`--no-file-parallelism`) and regardless of `pool`/`isolate` settings.
- **Evidence:**
  - Binary search over an ordered subset of `test/*.test.ts` (`head -N test-file-list.txt`) isolated the flip to including `test/indexing-version-runtime-dependencies.test.ts`... but pairing that file alone with the bun test did not reproduce it, so file *count*, not identity, was the proximate trigger.
  - Patched `@vitest/coverage-v8`'s `onAfterSuiteRun` (temporary, local `node_modules` edit, not committed) to dump each per-file raw V8 coverage batch. The raw batch for `test/bun-binary-update-instruction.test.ts` alone showed the correct hit counts (`getSelfUpdateUnavailableInstruction` ranges `[(5396,6564,count=2),(5674,6563,count=0)]`), proving the bug is not in test execution.
  - Kept the raw `coverage/.tmp/coverage-*.json` files (temporary patch skipping `cleanAfterRun`'s `rm`) and replayed `mergeProcessCovs` from `@bcoe/v8-coverage` locally over all 110 files: the merged result collapsed to a single zero-count range at the wrong byte offset. Removing exactly one file's raw JSON (`coverage-16.json`, from `test/indexing-version.test.ts`) restored the correct merged ranges.
  - `coverage-16.json` contained **two** separate raw script entries for the exact same URL (`.../src/config/install-paths.ts`): the normal 40-function/24175-byte script, and a second, differently-shaped 20-function/6551-byte script. Only `test/indexing-version.test.ts` produced this duplicate; every other file's batch had exactly one script per URL.
  - Root of the duplicate: `test/indexing-version.test.ts` had a single `require("../src/core/indexing-service.ts")` call (line ~267) inside an otherwise all-ESM (`import`) test file. Vitest's CJS-interop bridge re-compiles the required module (and its transitive dependencies, including `install-paths.ts` via `config.ts`) as a second, differently-wrapped script under the same file URL. `@bcoe/v8-coverage`'s `mergeProcessCovs` assumes one canonical script per URL with stable byte offsets; merging the mismatched second script corrupted the accumulated ranges for every other file's contribution to that URL for the rest of the run.
- **Approaches tried:**
  - **Attempt:** Suspect that `test/vitest-setup-isolated-agent-dir.ts` importing `src/config/constants.ts` (eagerly, before the bun test's `vi.mock` on that same module) caused a mock/module-graph collision.
    - **Outcome:** Did not work.
    - **Why:** Replacing the setup file's import with hardcoded literal env-var strings (removing the `src/config/constants.ts` import entirely) did not fix the reproduction at 200 files — ruled out.
  - **Attempt:** Disable V8 bytecode flushing (`execArgv: ["--no-flush-bytecode"]`, via Vitest 4's top-level `test.execArgv` — note `test.poolOptions` was removed in Vitest 4 and silently ignored) on the theory that GC-driven bytecode flushing of early-executed, later-unused functions was dropping coverage counts.
    - **Outcome:** Did not work.
    - **Why:** Confirmed the flag was actually forwarded to forked workers (verified via `process.execArgv` in a probe test), but the 110-file reproduction still failed. The real defect was in the coverage merge step, not V8's bytecode lifecycle.
  - **Attempt:** Force a single fork process for the whole run (`--no-file-parallelism`) to rule out cross-process/cross-worker lcov merge issues.
    - **Outcome:** Reproduced the bug anyway (informative negative), which correctly pointed at an intra-process merge defect rather than a multi-worker merge defect.
- **Root cause:** A test file used `require()` (Vitest's CJS-interop shim) to load a TypeScript source file that is also reachable via normal ESM `import` elsewhere in the same run. This produces a second, differently-transformed V8 script sharing the same file URL as the "real" ESM-compiled module. When `@vitest/coverage-v8` merges all per-file raw V8 coverage JSON blobs across the whole test run via `@bcoe/v8-coverage`'s `mergeProcessCovs`, it assumes exactly one script shape per URL; the mismatched second script's byte ranges silently corrupt the merged result for every other test file's contribution to that same source file, not just the offending file's own coverage.
- **Resolution:** Removed the `require("../src/core/indexing-service.ts")` call in `test/indexing-version.test.ts` and replaced it with a normal top-level static `import` of the two constants it needed (`INDEXING_SERVICE_STATUS_FILE`, `INDEXING_SERVICE_REINSTALL_FILE`), matching the rest of the file's ESM style and the repo's no-inline-import rule.
- **Verification:** Full `packages/coding-agent` `npm run test:coverage` run after the fix shows `src/config/install-paths.ts` `DA:82,4` / `DA:83,4` / `DA:84,2` / `DA:86,2` (all covered) in `coverage/lcov.info`. `npm run test:coverage:check -- --base origin/main` (i.e. `node scripts/check-changed-coverage.js --base origin/main`) exits 0 with `Coverage: 100.00% (required: 99%)`. `scripts/check-changed-coverage.test.js` (`node --test`) still passes unchanged.
- **Prevention/follow-up:** Avoid `require(...)` on TypeScript source files inside Vitest test files in this repo — always use a static `import`; a CJS `require()` of an ESM-reachable module can silently corrupt v8 coverage attribution for unrelated files elsewhere in the same run, with no functional test failure to signal it. Consider a lint rule or `grep`-based CI check banning `require(` in `packages/*/test/**/*.test.ts` if this recurs.
- **Reusable learning:** When a full-suite `@vitest/coverage-v8` run shows a source line as uncovered but an isolated/small-subset run of the exercising test shows it covered, suspect a *different* test file elsewhere in the run that loads the same module through a second code path (CJS `require()` alongside ESM `import`, or a differently-configured `vi.mock`) — it can corrupt `mergeProcessCovs`'s cross-file merge for that shared URL without breaking any test assertion.
- **References:** `packages/coding-agent/test/indexing-version.test.ts`, `packages/coding-agent/src/config/install-paths.ts`, `packages/coding-agent/src/core/indexing-service.ts`, `scripts/check-changed-coverage.js`, `.changes/fix-indexing-version-test-coverage-corruption.json`.
