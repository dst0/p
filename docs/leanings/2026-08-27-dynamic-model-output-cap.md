# 2026-08-27 — Dynamic model output cap

- **Status:** Resolved
- **Task/context:** Follow-up review of pre-request context budgeting for small-window providers and explicitly raised output limits.
- **Unexpected observation or failure:** Treating serialized UTF-8 bytes as tokens falsely rejected normal ASCII requests, while reserving a model's full advertised output made the compaction threshold zero when `maxTokens === contextWindow`; even an empty prompt plus the safety margin could never pass.
- **Evidence:** A 52,206-byte unchanged ASCII payload represented only about 13,052 tokens under the repository estimate, but the byte-as-token guard rejected it against a 48,128-token input budget. P normally requests at most 16,384 output tokens, so equal metadata caps on larger windows remain usable; the concrete default-path failure occurs when the context window is at or below 17,408 tokens, while larger windows encounter the same impossible reservation only when the request cap is explicitly raised far enough.
- **Approaches tried:**
  - **Attempt:** Use UTF-8 byte length as a universal token upper bound.
    - **Outcome:** Did not work
    - **Why:** It prevented non-ASCII undercounting but falsely treated ordinary multi-byte serialized request overhead as provider tokens and could reject immutable system prompts and tool schemas that actually fit.
  - **Attempt:** Always reserve and send the full advertised output cap.
    - **Outcome:** Did not work
    - **Why:** A full-window output cap leaves no capacity for any prompt or safety margin, so compaction cannot make the desired budget attainable.
  - **Attempt:** Keep the advertised/requested cap as the compaction target, then clamp the actual call to the positive capacity left after the final prompt estimate and safety margin.
    - **Outcome:** Worked
    - **Why:** Normal 16k calls remain unchanged, useful prior history is compacted once before reducing output, intrinsically impossible full-window reservations immediately receive a positive bounded cap, and successful compaction can restore the original desired cap on the rebuilt request.
- **Root cause:** The earlier design conflated three different quantities: an approximate provider prompt token count, serialized byte growth introduced by a late hook, and a model's advertised maximum output. It also propagated a pre-compaction reduced cap as the next retry's desired cap and treated threshold compaction's continuation boolean as proof that no compaction boundary was written.
- **Resolution:** Use the existing character-based prompt estimate for preflight, retain UTF-8 only as a no-growth comparison against the exact baseline payload, preserve output-cap field paths and prevent increases above their baseline values, and compute each call cap as `min(desired, contextWindow - promptEstimate - 1024)`. Compact at most once only when the desired cap can theoretically fit and assistant history exists; detect success by the persisted compaction boundary, recompute from the rebuilt context, degrade to the reduced positive cap when no boundary is produced, and fail only when no positive response capacity remains. Tool-less contexts use an empty tool list.
- **Verification:** `agent-session-dynamic-output-cap.test.ts` proves a real 16,384-context first request with default active tools and an equal advertised output cap reaches the provider once with a reduced positive cap and no compaction loop, and proves a reduced pre-compaction budget returns to the full desired 16k after a successful rebuild. `agent-session-preflight-context-budget.test.ts` proves a realistic 65,536-context request keeps the normal 16k cap, each request's actual cap plus prompt estimate and margin fits, and a static payload with no positive capacity fails before provider I/O. `model-call-budget.test.ts` covers realistic unchanged ASCII payloads, same-character non-ASCII hook growth, tool-less contexts, and output-cap path/value preservation.
- **Prevention/follow-up:** Keep desired output, actual per-call output, and late-hook payload growth as separate invariants. Generation continuity must treat a provider length stop from an intentionally reduced cap as resumable work rather than as a failed or completed task.
- **Reusable learning:** An advertised maximum is a ceiling, not a reservation. Compact toward it when useful, but derive the final request cap from the exact current prompt budget and preserve the original desired cap across rebuild retries.
