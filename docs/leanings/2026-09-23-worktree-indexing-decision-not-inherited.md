# 2026-09-23 — Linked git worktrees re-prompted for an indexing decision already made in the main checkout

- **Status:** Resolved
- **Update:** A follow-up critic review found the resolution below persisted/auto-indexed the worktree and re-shelled to git on every 500ms footer poll; see `2026-09-23-worktree-indexing-inheritance-revised-no-persist-cache-git.md` for the corrected design (no persistence, no auto-indexing, and per-process caching). The root-cause diagnosis in this file is still accurate.
- **Task/context:** Fixing a bug report that `p` shows a blocking "index this repo?" modal for every new `git worktree` of a repository whose main checkout already has a saved indexing decision (enabled or disabled).
- **Unexpected observation or failure:** `IndexingService.getDecision()` (`packages/coding-agent/src/core/indexing-service.ts`) always returned `"unknown"` for a freshly created linked worktree, even though the main checkout's decision was already persisted in `indexed-repos.json`, so `do_promptForCodeIndexingIfNeeded` (`extension-ui-context.ts`) showed the modal again.
- **Evidence:** `findWorkspaceRoot` (`workspace-root.ts`) stops at the worktree's own `.git` file (a `gitdir:` pointer), so it never walks up to the main checkout. `computeRepoId` (`indexed-repos.ts`) hashes `repoPath + origin remote`, so the worktree's distinct `repoPath` produces a distinct `repoId`. `findEntry` then matches neither by canonical path nor by `repoId`, so `getRepoIndexingDecision` returns `"unknown"` for the worktree even when the main checkout's entry exists.
- **Approaches tried:**
  - **Attempt:** Make `findWorkspaceRoot`/`computeRepoId` treat a linked worktree's canonical root as the main checkout's root.
    - **Outcome:** Not used
    - **Why:** Would change the identity every other indexing code path (daemon runtime keys, `isRepoIndexed`, semantic search) uses for a worktree, and would make the worktree's own indexed content get discarded/overwritten by the main checkout's status — too invasive for the actual bug, which is only about the one-time decision prompt.
  - **Attempt:** Resolve the main worktree via `git rev-parse --git-common-dir` at the decision-lookup call site (`IndexingService.getDecision`), and if the current repo's own decision is `"unknown"`, look up the main worktree's decision and reuse it (persisting an `enabled`/`disabled` entry for the worktree's own path so it is not asked again and, if enabled, so the daemon's registry sync picks it up as its own indexing root).
    - **Outcome:** Worked
    - **Why:** `git rev-parse --path-format=absolute --git-common-dir` reliably resolves to `<main>/.git` for a linked worktree, but is *not* named `.git` for a bare repo (e.g. `repo.git`) or a `--separate-git-dir` checkout (an arbitrary external path), and is nested under `.git/modules/<name>` for a submodule — so requiring `path.basename(gitCommonDir) === ".git"` plus a real `.git` directory (not a gitfile) at its parent cleanly rejects all three cases and falls back to prompting as before, without needing special-case detection code for each.
- **Root cause:** The worktree's own `repoId`/path never matched any existing `indexed-repos.json` entry, and nothing looked at the main checkout on the worktree's behalf.
- **Resolution:** `IndexingService.getDecision` (`packages/coding-agent/src/core/indexing-service.ts`) now falls back to the main worktree's decision via a new `findMainWorktreePath` helper in `packages/coding-agent/src/core/workspace-root.ts`, and persists that inherited decision under the worktree's own path (enabling background indexing immediately for `"enabled"`, and silently recording `"disabled"` so it is not asked again).
- **Verification:** New regression tests in `packages/coding-agent/test/indexing-worktree-decision-inheritance.test.ts` use real `git init` + `git worktree add` repos (no git mocks): confirmed failing against the pre-fix code (modal shown for both an enabled and a disabled main checkout), then passing after the fix. Also verified a non-worktree repo still prompts, and a worktree whose main checkout is a bare repo still falls back to prompting. `npm run check` and the full `indexing-service.test.ts`/`indexed-repos.test.ts`/`interactive-mode-indexing-prompt.test.ts`/`workspace-root.test.ts` suites pass.
- **Prevention/follow-up:** None outstanding; the guard logic (basename check + real `.git` directory + `HEAD` file) is exercised directly by the bare-repo regression test. A future change to `computeRepoId`/`findWorkspaceRoot` worktree identity should re-check this inheritance path.
- **Reusable learning:** When per-repo state needs to be resolved for a linked `git worktree`, don't assume its own working-tree root is a safe identity key — use `git rev-parse --git-common-dir` to find the real backing checkout, but always guard on the common dir's basename being exactly `.git` (with a real directory, not a gitfile, at its parent) before trusting it as "the main worktree": that one check is what excludes bare repos, `--separate-git-dir`, and submodule gitdirs without bespoke detection for each.
- **References:** `packages/coding-agent/src/core/indexing-service.ts`, `packages/coding-agent/src/core/workspace-root.ts`, `packages/coding-agent/src/core/indexed-repos.ts`, `packages/coding-agent/test/indexing-worktree-decision-inheritance.test.ts`.
