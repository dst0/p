# 2026-09-26 — Global p runtime was linked to a mutable checkout

- **Status:** Resolved
- **Task/context:** Reinstall and release readiness across several p worktrees.
- **Unexpected observation or failure:** The global `p` command and persistent indexing daemon could execute from whichever worktree last ran `./reinstall.sh`. A later checkout change or worktree removal could break the installed agent.
- **Evidence:** Before the fix, `/opt/homebrew/bin/p` resolved through npm workspace links to `packages/coding-agent/dist/cli.js` in a development checkout; the daemon status recorded that checkout's `dist/indexing-service-daemon.js` and root. The old `reinstall.sh` called `npm link -w @dst0/p` in its source directory.
- **Approaches tried:** A packed npm production runtime was reviewed, but the existing service installer and version/provenance paths assume the monorepo layout, making that a larger simultaneous migration. A committed-source snapshot preserves that layout and executes existing build and service checks from the installed copy.
- **Root cause:** Reinstall treated a source checkout as both build source and durable installation target.
- **Resolution:** Reinstall now requires a clean committed source, stages its exact Git archive under a fresh `~/.p/install/versions/` directory, builds and links from there, and updates `current` only after health verification. An already installed runtime is never rebuilt in place. A per-home lock under `~/.p/install` serializes global CLI and service mutations even when custom agent directories differ; the per-agent lock separately protects indexing state. Both stay owned by the outer process through candidate installation and restoration, so a failed concurrent attempt cannot restore a stale predecessor over a newer success. `previous` retains the prior successful runtime; an actual rollback reruns its `reinstall.sh` to repoint both the CLI and service. Mutable settings and Qdrant storage stay in their existing agent/data locations.
- **Verification:** Focused snapshot and transaction tests cover clean/dirty sources, isolation, fresh same-SHA staging, activation, symlink and writable-parent rejection, cross-agent-directory serialization, EXIT-trap status and both lock releases, candidate failure, and previous-runtime restoration. An adversarial review found that checking only the CLI version or daemon readiness could accept a different installed runtime, so the installer now requires the CLI realpath and daemon provenance to match the exact candidate; the latter has a focused regression. Full validation and live reinstall results belong in the PR verification record.
- **Prevention/follow-up:** Keep the installed runtime separate from worktrees. Do not prune older installed versions automatically; inspect the active CLI and daemon paths before retiring any runtime. A first install has no centralized fallback and requires explicit path inspection if it fails.
- **Reusable learning:** Build source and installed execution path are separate identities; verify both before claiming an installation is durable.
- **References:** `reinstall.sh`, `scripts/central-install-snapshot.js`, `scripts/central-install-snapshot.test.js`.
