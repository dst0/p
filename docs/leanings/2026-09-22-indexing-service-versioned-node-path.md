# 2026-09-22 — Service definitions must not pin a Homebrew Cellar Node path or the installing shell's raw PATH

- **Status:** Resolved
- **Task/context:** Keep the `com.dst.p.code-index` launchd/systemd service startable across routine Node upgrades. The installer (`scripts/install-indexing-service.js`) renders the service from `buildServiceValues()` in `scripts/indexing-install-fallback.js`.
- **Unexpected observation or failure:** The installed launchd plist launched `/opt/homebrew/Cellar/node/26.8.1/bin/node`. `brew upgrade node` deletes that versioned directory, after which launchd cannot start the daemon. The same plist's `PATH` held the venv directory plus 22 entries copied from the installing shell, including a Codex session scratch directory under `~/.codex/tmp/arg0/`, four directories that no longer existed, and repeated `/opt/homebrew/bin` and `~/.local/bin` entries.
- **Evidence:** `process.execPath` under Homebrew is the resolved Cellar path, while `/opt/homebrew/bin/node` is a relative symlink (`../Cellar/node/26.8.1/bin/node`) that Homebrew repoints on upgrade. The installer wrote `node: process.execPath` and `PATH: <venv>:${process.env.PATH}` verbatim. Eight new wiring tests driven through `buildServiceValues()` failed against the unchanged code with the Cellar path and the unsanitized inherited `PATH`.
- **Approaches tried:**
  - **Attempt:** Keep `process.execPath`.
    - **Outcome:** Did not work.
    - **Why:** Node resolves its own executable path, so every Homebrew install records a directory that the next upgrade removes.
  - **Attempt:** Launch plain `node` through the service `PATH`, or render a fixed minimal `PATH`.
    - **Outcome:** Rejected.
    - **Why:** Resolving `node` through `PATH` at service start can pick an nvm or other Node release that the checkout was not installed or smoke-tested with. A fixed `PATH` can drop tools the daemon and GPU/NPU runtimes rely on, such as Homebrew `git` or vendor toolchains.
  - **Attempt:** Prefer the first `node` on the sanitized `PATH` whose realpath equals `realpath(process.execPath)` and whose own path has no dotted version, `Cellar`, or `fnm_multishells` segment and is not a `/snap/<name>/<revision>` path. Otherwise fall back to `process.execPath` and warn when that path is version-scoped. Also sanitize the inherited `PATH`.
    - **Outcome:** Worked.
    - **Why:** The service keeps the exact binary the installer ran and smoke-tested, but reaches it through the package manager's stable link.
- **Root cause:** The installer stored runtime-resolved and session-scoped values (the running binary's realpath and the interactive shell's `PATH`) in a long-lived service definition.
- **Resolution:** Added `scripts/indexing-service-node-executable.js` (`resolveStableNodeExecutable`, `isVersionScopedPath`) and `scripts/indexing-service-search-path.js` (`sanitizeServiceSearchPath`, `isTemporaryDirectory`, `isUnderTemporaryRoot`). `buildServiceValues()` now uses them and keeps the managed venv first. Both modules are tracked by `computeIndexingVersion()`. That changes the indexing version, so the next reinstall does a full launchd bootout and bootstrap instead of the reuse path. The reuse path rewrites the plist file without reloading the job, so launchd would otherwise keep the cached Cellar path.
- **Verification:** `node --test scripts/indexing-service-node-executable.test.js scripts/indexing-service-search-path.test.js` covers a Homebrew-like fixture, the fallback, a realpath mismatch, version- and session-scoped links, and PATH sanitization. The vitest dependency test failed with the original `installerNames` and passes with the new entries. An adversarial review found four tests passing without the code they named: the process-default wiring, the filesystem-root guard, the unresolvable-executable guard, and the `Cellar` segment for `HEAD-<sha>` builds. After the tests were tightened, all 23 targeted source mutations of the two modules and `buildServiceValues()` fail at least one test. A read-only probe on the affected Mac resolved `/opt/homebrew/bin/node` and reduced a 53-entry shell `PATH` to the venv directory plus 28 existing, non-temporary, unique entries.
- **Prevention/follow-up:** Never render `process.execPath` or `process.env.PATH` verbatim into launchd or systemd definitions. Resolve them to stable, existing, non-temporary locations and test the rendered unit. Open follow-ups: (1) the daemon script path still points into the checkout used for reinstall, so reinstalling from a disposable worktree binds the service to that worktree; (2) when the indexing version is unchanged, the reuse path rewrites the launchd plist without reloading the job, so a changed Node path or `PATH` takes effect only after the next full reinstall; (3) snap installs are only warned about, not redirected to `/snap/<name>/current`; (4) the `tmp`/`temp` segment rule is lexical, so a stable-looking symlink into such a directory is kept. Fixtures that test path policy must not live under directories that the policy itself classifies: on Linux, `os.tmpdir()` is `/tmp`, so negative controls for segment rules cannot use `mkdtemp` fixtures.
- **Reusable learning:** A long-lived service must reference package-manager-stable links, not the realpath of the process that installed it. Filter inherited environment paths for existence, temporariness, and duplicates before persisting them.
