# 2026-09-23 — Worktree indexing-decision inheritance needed a cache and must not auto-index or persist

- **Status:** Resolved
- **Task/context:** Follow-up critic review of the fix in `2026-09-23-worktree-indexing-decision-not-inherited.md`, which made a linked `git worktree` inherit its main checkout's saved indexing decision (`enabled`/`disabled`) instead of re-prompting. The review found two problems with that first iteration before it was published further.
- **Unexpected observation or failure:**
  1. **Perf/HIGH:** `FooterDataProvider` polls `IndexingService.getStatus()` (which calls `getDecision()`) every 500ms (`footerdataprovider.ts`, `INDEXING_STATUS_POLL_MS`). The first iteration's inheritance fallback ran `git rev-parse --git-common-dir` (via the new `findMainWorktreePath`) plus, transitively, `computeRepoId`'s `git remote get-url origin` for the main checkout, on every single poll tick for any repo whose own decision was `"unknown"` — spawning two extra git subprocesses per tick, forever, on the TUI thread.
  2. **Design:** The first iteration persisted the inherited decision under the worktree's own path (`enableIndexingForRepo`/`disableIndexingForRepo`) so an inherited `"enabled"` would make the background daemon index the worktree. The reviewer pointed out this is wrong for how worktrees are actually used here: the repo owner creates and removes many short-lived worktrees, each of which would be fully re-embedded (expensive, and largely redundant with the main checkout's index), and the persisted registry entries for removed worktrees would go stale.
- **Evidence:** Manually walked the poll path (`footerdataprovider.ts:119` → `label-formatting.ts:51` `do_refreshIndexingStatus` → `IndexingService.getStatus` → `getDecision`) and confirmed no memoization existed on the worktree→main resolution added in the first iteration.
- **Approaches tried:**
  - **Attempt:** Keep persisting the inherited decision (first iteration), just add a cache to stop the per-tick git spawn.
    - **Outcome:** Not used
    - **Why:** Caching alone doesn't fix the design problem — an inherited `"enabled"` would still write a permanent-looking registry entry and kick off a full background re-embedding for every worktree the user creates, which is the opposite of the desired "cheap, disposable worktree" experience.
  - **Attempt:** Never persist or auto-index for a worktree; only suppress the prompt when the main checkout has *any* explicit decision (enabled or disabled), and expose this as a distinct `inheritedFrom` field on `RepoDecisionInfo`/`IndexStatus` for display (`/index`, footer) — plus memoize the worktree→main resolution (both the git-common-dir lookup in `workspace-root.ts` and the composite "does main have a decision" check in a new `indexing-decision-inheritance.ts`) per `(agentDir, workspaceRoot)` for the lifetime of the process.
    - **Outcome:** Worked
    - **Why:** The repo's own decision (`getRepoIndexingDecision(workspaceRoot)`) is checked *before* consulting the cache or resolving the main worktree at all, so an explicit `/index enable`/`disable` on the worktree itself always bypasses the inherited-decision cache and persists normally — no cache invalidation is needed. And because nothing is ever persisted for the worktree on the inherited path, "resolve once per process" is an acceptable simplification: if the main checkout's decision changes mid-session, the running worktree session keeps its already-resolved answer until restart, which the reviewer explicitly approved as the desired trade-off.
- **Root cause:** The original fix reused `getRepoIndexingDecision`/`enableIndexingForRepo` (registry-persisting APIs) without considering (a) how often the resolution would be re-entered by the footer's poll loop, and (b) that "the worktree should behave as this decision" is not the same claim as "the worktree should be indexed like the main checkout".
- **Resolution:**
  - `packages/coding-agent/src/core/indexing-decision-inheritance.ts` (new file): `resolveRepoDecision(workspaceRoot, agentDir)` returns `{ decision, inheritedFrom? }`, never persists anything, and caches the resolved result per `(agentDir, workspaceRoot)` once the repo's own decision has been found `"unknown"`.
  - `packages/coding-agent/src/core/workspace-root.ts`: `findMainWorktreePath` now caches its result (including the "not a worktree" `undefined` outcome) per canonical `workspaceRoot`, and passes `timeout: 2_000` to `execFileSync` so a hung/slow git process can't block the TUI thread indefinitely — the existing try/catch still falls back to prompting silently on any failure, including a timeout.
  - `packages/coding-agent/src/core/indexing-service.ts`: `getDecision`/`getStatus` delegate to `resolveRepoDecision`; `IndexStatus` gained `inheritedFrom?: string`. `enableIndexing`/`disableIndexing` are unchanged (still the only way to persist a decision) and are no longer called from the inheritance path.
  - `do_promptForCodeIndexingIfNeeded` (`extension-ui-context.ts`) now checks `resolveDecision(...).inheritedFrom` in addition to `decision !== "unknown"` before showing the modal.
  - `do_buildIndexStatusText` (`status-command.ts`) shows `"inherits main checkout (not indexed): <path>"` for `/index` when `inheritedFrom` is set instead of `"not configured"`.
- **Verification:** Rewrote `packages/coding-agent/test/indexing-worktree-decision-inheritance.test.ts` (real `git init`/`git worktree add`, no git mocks — `node:child_process`'s `execFileSync`/`execSync` are wrapped with a pass-through `vi.fn()` spy via `vi.mock` purely to count real invocations). Confirmed regressions before reapplying the fix using **patch files, not `git stash`**: saved the fixed source as a patch (`git diff` after `git add -N` for the new file), reverse-applied it with `git apply -R` to prove the persisting/auto-indexing design regressed (2 tests failed: `getDecision(worktree)` came back `"enabled"`/`"disabled"` instead of staying `"unknown"`), then `git apply`'d it back. Separately proved each cache layer catches its own regression by editing in a disabled/no-op cache (kept as an on-disk copy of the fixed file for exact restoration): with the `indexing-decision-inheritance.ts` cache disabled, 10 `getDecision`/`getStatus` calls produced 10 `git remote get-url origin` calls instead of 1; with the `workspace-root.ts` cache also disabled, the same loop produced 10 `git rev-parse --git-common-dir` calls instead of 1. Restored both files and re-ran: all 6 tests pass. Ran `npm run check` (biome, file-structure, pinned-deps, ts-imports, shrinkwrap, tsgo x2, browser-smoke) clean, plus the full `indexing-service.test.ts`/`indexed-repos.test.ts`/`interactive-mode-indexing-prompt.test.ts`/`workspace-root.test.ts`/`footer-data-provider.test.ts` suites (68 tests, all passing).
- **Prevention/follow-up:** None outstanding. Future changes to `resolveRepoDecision`'s cache should keep the invariant that the repo's *own* decision is always checked before the cache, so explicit `/index enable|disable` never needs manual cache invalidation.
- **Reusable learning:** Before adding a fallback/derived-state lookup to a code path a UI already polls on a timer, check every poller of that path first (`grep` for the reader, not just the obvious caller) — a "one-time" decision lookup can silently become a per-tick subprocess spawn. And when a linked resource (like a `git worktree`) is meant to be cheap and disposable, "inherit a setting for display/prompt purposes" and "inherit a setting that triggers expensive background work" are different claims — don't conflate them by reusing the same persist-and-act API for both.
