# 2026-09-23 — Verification ceremony must scale with the task

- **Status:** Resolved
- **Task/context:** Make `p` practical as a daily driver on local open-weights models (Qwen 27B behind an OpenAI-compatible orchestrator, about 700 tok/s prefill and 24 tok/s decode) without weakening verification of code changes.
- **Unexpected observation or failure:** Trivial prompts paid the full evidence protocol. "What is 17*23? Reply with just the number." answered `391`, then `finish_work` was rejected for a missing checklist, then `record_task_verification`, then `finish_work`. The run took about 45 s and three extra turns. "Read package.json and report one script" took 79 s over three model calls and five tool calls, and only `read` was useful.
- **Evidence:** A faux-provider capture of the first request for the arithmetic prompt, taken with `createAgentSession`, legacy project instructions, and no extensions, measured 17,126 system-prompt characters and 13 tools totalling 13,264 schema characters (≈7.6k tokens). With the model answering in text every turn, the explicit protocol consumed four provider calls. After the change, the default LIGHT request measures 3,564 system-prompt characters and 7 tools totalling 5,894 schema characters (≈2.4k tokens), and the run ends after one call. The 20 record_task_verification guideline bullets, the session-state protocol, and the completion block were the largest single costs.
- **Approaches tried:**
  - **Attempt:** Hybrid completion (request `finish_work`, then fall back to implicit).
    - **Outcome:** Did not work.
    - **Why:** The no-progress stop fires after six turns, before the implicit fallback at sixteen, and every repair turn still pays a full prefill.
  - **Attempt:** A separate classifier model call per prompt.
    - **Outcome:** Rejected.
    - **Why:** It adds 3–8 s per prompt, risks KV-cache eviction or a model switch on a single-GPU orchestrator, and the local compiler endpoint already failed.
  - **Attempt:** LIGHT by default with a deterministic prior, a model signal (`begin_code_task`), and an effect backstop that escalates to STRICT.
    - **Outcome:** Worked.
    - **Why:** The prior costs nothing. The model signal rides along with the first edit, so it adds no round trip. The backstop catches undeclared code edits, and escalation reuses the unchanged evidence engine.
- **Root cause:** The verification policy was global and static, so the evidence engine and explicit completion applied to every prompt regardless of whether code was changed.
- **Resolution:** `taskVerification.mode` defaults to `auto`. LIGHT uses a short prompt, a reduced tool set, implicit completion, and an observe-only controller. STRICT is today's evidence engine. It is reached by prior, by `begin_code_task`, or by the first source, test, or build-config change. Mid-run escalation switches tools and the system prompt, flips completion through `AgentLoopTurnUpdate.completionMode`, and appends a short notice. The escalation also restarts the protocol turn budget. Under `auto`, a zero-effect STRICT task ends with plain text. If the request asked for a change, the first text-only answer gets one repair, and a successful `finish_work` without any change is rejected. `strict` reproduces the previous behavior exactly, and its first request is byte-identical to the pre-change request.
- **Verification:** Agent-loop tests cover the completion-mode flip and the `allowImplicitCompletion` hook. Unit tests cover the policy, the prior, path classification, and the tier state machine. Faux-provider suites cover the LIGHT, escalation, persistence, `/verify`, and unknown-effect scenarios. An SDK test enforces the first-request budget and checks that resume restores the tier. The existing evidence and audit suites pass unchanged under forced STRICT.
- **Prevention/follow-up:** The first-request budget test fails if LIGHT regrows its prompt or tool set. An adversarial test review found that an unobserved extension call could leak into the ledger when a parallel edit escalated mid-batch. The controller now records its observe-only decision per tool call, and a synchronized parallel-batch regression covers it. Still to do: benchmark `auto` against `strict` on the macro suite, and measure the auto-activated extension tools that dominate the owner's real 22k-token first request.
- **Reusable learning:** On slow local models, every protocol turn costs a full prefill. Default to the cheapest protocol that is safe, and escalate on concrete evidence, such as a code edit or the model's own declaration, rather than paying ceremony up front.
