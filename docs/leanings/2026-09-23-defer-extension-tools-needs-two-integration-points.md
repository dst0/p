# 2026-09-23 — Deferring extension/MCP tools under LIGHT needs two integration points, not one

- **Status:** Resolved
- **Task/context:** Fix `do__refreshToolRegistry` (packages/coding-agent/src/core/agent-session/agentsession-methods/tool-registry.ts) auto-activating every extension/MCP tool with a `promptSnippet`, which defeated the LIGHT verification tier's small system prompt. The task's owner reported observing 13.5K vs 3.9K static context tokens with their own real extension config; this was the reporter's own before/after comparison, not a figure this session measured or that CI has verified — actual before/after measurement on a real config is expected to happen separately, post-merge. This session's own measurement (one fake tool, isolated test harness) showed a 230-char reduction in system prompt + tool schema footprint (8975 vs 9205 chars for LIGHT-deferred vs `never`), which is directionally consistent but much smaller in scale. The fix generalizes the existing `LIGHT_DEFERRED_TOOL_NAMES` deferral (packages/coding-agent/src/core/task-verification/task-tier.ts) to non-builtin tools, gated by a new `tools.deferExtensionTools` setting (`light` default, `always`, `never`).
- **Unexpected observation or failure:** A single fix at the activation site (checking the current tier in `do__refreshToolRegistry` before eagerly activating a promptSnippet tool) was not sufficient. Two existing tests broke when the fix was applied naively:
  - `test/suite/adaptive-verification-unknown-effect-tools.test.ts`
  - `test/suite/adaptive-verification-large-workspace.test.ts`

  Both register their fake tool at the top level of the extension factory (`p.registerTool({...})` called directly, not inside `p.on("session_start", ...)`). That is a first-class, documented pattern (`registerTool() is valid during extension load; refresh is only needed post-bind`, packages/coding-agent/src/core/extensions/loader.ts). Tools registered this way are already present in `self._extensionRunner.getAllRegisteredTools()` at the very first `do__refreshToolRegistry` call inside the `AgentSession` constructor — which runs *before* `installTaskVerificationRuntime` wires up `session._taskVerificationRuntime`. At that first call, `isLightTierActive(self)` cannot know the tier yet (the runtime does not exist), so it falls back to "not light" and eagerly activates the tool, exactly like before the fix. Only a *second* refresh (e.g. one triggered by `bindExtensions` → `session_start` → `registerTool` → `refreshTools()`) would see the tier correctly — but nothing re-registers an already-registered tool, so no second refresh happens for this pattern.
- **Evidence:** Running the two named test files against a version of the fix that only checked the tier inside `do__refreshToolRegistry` (no change to `tierManagedToolNames`) reproduced the pre-fix behavior: `web_search_exa`/`secure_hub_workspace_task_write`/`remote_patch` stayed active from turn 1 under the default `auto` (LIGHT) policy, because they were already in the active-tool snapshot before the tier was known.
- **Approaches tried:**
  - **Attempt:** Only gate the eager-activation loop in `do__refreshToolRegistry` on `isLightTierActive(self)` plus the new setting.
    - **Outcome:** Partial
    - **Why:** Correctly defers tools registered *after* `installTaskVerificationRuntime` (the common `session_start`-gated pattern used by `regressions/3592-*` and `regressions/5109-*`), but does nothing for tools already active in the very first `getActiveToolNames()` snapshot the tier runtime sees — including eagerly-registered extensions and, in principle, tool names carried over from a resumed session's persisted branch.
  - **Attempt:** Additionally generalize `tierManagedToolNames` in `installTaskVerificationRuntime` (packages/coding-agent/src/core/task-verification-session-runtime.ts) to include any *currently active*, non-builtin, promptSnippet-bearing tool name (via `deferrableExtensionToolNames` in task-tier.ts), reusing the exact same LIGHT/STRICT toggle (`verificationTierToolNames`) that already handles the static `LIGHT_DEFERRED_TOOL_NAMES` builtins.
    - **Outcome:** Worked
    - **Why:** This mechanism runs *after* the tier is known (at `installTaskVerificationRuntime` time) and captures whatever is active *at that moment*, regardless of when/how it got activated. Confirmed by temporarily reverting just this piece and re-running the two existing tests: `adaptive-verification-unknown-effect-tools.test.ts` failed again (`web_search_exa` stayed active turn 1) while the do__refreshToolRegistry-only fix looked complete in isolation.
- **Root cause:** Extension tools can become "active" through two structurally different lifecycle paths relative to when the verification tier becomes known: (1) registered before the tier runtime exists (eager, top-level `registerTool`, or carried over from a resumed session), and (2) registered/refreshed after the tier runtime exists (`session_start`-gated `registerTool`, `/reload`). A fix at only one integration point silently misses the other.
- **Resolution:** Implemented both integration points, driven by the same `tools.deferExtensionTools` setting and the same "non-builtin + has promptSnippet" predicate: `do__refreshToolRegistry` gates its eager-activation loop on `isLightTierActive` (packages/coding-agent/src/core/agent-session/agentsession-methods/tool-registry.ts), and `installTaskVerificationRuntime` folds any already-active matching tool names into `tierManagedToolNames` (packages/coding-agent/src/core/task-verification-session-runtime.ts), so `verificationTierToolNames` — the single existing LIGHT/STRICT toggle — governs both. Updated `adaptive-verification-unknown-effect-tools.test.ts` and `adaptive-verification-large-workspace.test.ts` to add a leading `tool_search` activation turn, since their MCP-style/eager tools now correctly defer under the default LIGHT tier and must be activated before the faux script calls them.
- **Verification:** New `test/suite/defer-extension-tools-light.test.ts` (5 cases: LIGHT deferral + tool_search activation + execution, STRICT unchanged, `never` setting restores old behavior, exact-name lookup for a weakly-described tool, and a char-count measurement of the LIGHT vs `never` system prompt + tool schema footprint). Verified each of the 4 key assertions fails against the pre-fix source (saved as a patch, reverted with `git restore`, re-applied with `git apply` — never `git stash`, per repository policy for shared worktrees). Full targeted suite (`defer-extension-tools-light`, both updated adaptive tests, all other `adaptive-verification-*` files, `verification-ledger`, regressions `3592`/`5109`, `subagent-extension-failure-semantics`) passes: 14 files, 67 tests. `npm run check` passes clean.
- **Prevention/follow-up:** If another activation-gating feature is added for extension tools in the future, check both lifecycle paths above before assuming a single call-site fix is complete — search for `p.registerTool` calls in extension factories/tests that are *not* wrapped in an event handler; those tools are active before `installTaskVerificationRuntime` runs.
- **Reusable learning:** In this codebase, an extension tool's activation-time behavior cannot be fixed at only the "activation" call site (`do__refreshToolRegistry`) when the desired condition (verification tier) is not yet known at every time that site runs. Any tier-dependent tool-activation policy needs a second check at the point where the tier state actually becomes available (`installTaskVerificationRuntime`/`verificationTierToolNames`), reusing the same predicate, or it will silently miss tools that were already active before the tier was resolved.
