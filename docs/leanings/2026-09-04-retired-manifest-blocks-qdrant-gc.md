# 2026-09-04 — A retired manifest can block all Qdrant collection GC

- **Status:** Partial
- **Task/context:** Diagnose unexpectedly large local Qdrant storage and safely reduce persisted startup work after an installer smoke exceeded its startup deadline.
- **Unexpected observation or failure:** The unmodified collection GC planner aborted with `Cannot safely read Qdrant collection reference`, caused by `Collection name is missing`. One July manifest used a retired version-2 status format with no `collection` field, while the same repository already had a valid manifest under its current identity.
- **Evidence:** A metadata-only inventory found 42 collections, 22 valid current manifest references, no checkpoints, one stale refresh lock, empty aliases, and standalone peer state. All 22 referenced collections existed. Allocated storage was 32.57 GiB versus 28.60 GiB of file lengths. Eighteen unreferenced managed generations older than 24 hours occupied 12.63 GiB. One recent unreferenced generation and the unknown legacy collection name were retained. The current repository identity was independently recomputed from canonical path plus NUL plus Git remote; the retired identity was absent from the registry.
- **Approaches tried:**
  - **Attempt:** Rely on the scheduled startup/daily GC to clear obsolete generations.
    - **Outcome:** Did not work.
    - **Why:** GC first requires a ready Qdrant backend, then requires every manifest/checkpoint reference to be readable. Backend startup and the retired-format manifest were independent blockers.
  - **Attempt:** Ignore the malformed manifest or treat every unreferenced directory as garbage.
    - **Outcome:** Rejected.
    - **Why:** That would remove a deliberate fail-closed boundary and could discard current or resumable data. Recent generations, unknown names, and manifests for absent repositories remain protected.
  - **Attempt:** Reversibly quarantine the proven-retired metadata, rerun the unchanged GC planner, and require the exact previously audited 18 collection names before same-device renames.
    - **Outcome:** Worked for reachability and active-set cleanup.
    - **Why:** Hash and identity checks established retirement without inventing references. Repeated reference/process/inventory checks and an append-only transaction journal recorded paths for supervised rollback; this does not establish power-loss durability. The final non-mutating GC pass retained 24 collections with no candidate deletions or errors.
- **Root cause:** A retired manifest persisted in the active reference namespace. The collector correctly rejected its missing collection identity, globally blocking cleanup. This explains the present GC failure; it does not establish the complete historical cause of every orphan or the separate storage-startup delay.
- **Resolution:** Eighteen old collection directories and the retired metadata were first moved to an explicit same-volume quarantine outside all Qdrant-managed paths. After successful retained-backend recovery, full archive restoration, and a fresh original-file hash/reference/writer check, exactly those 19 raw directories were removed. Their bytes remain recoverable in the 949,777,991-byte Brotli Q6 archive plus its mandatory 19,336-byte sidecar supplement. No active manifest was rewritten, no currently referenced collection was removed, and no GC safety check was weakened. The separate recent failing generation remains intact in incident quarantine.
- **Verification:** The initial five operational tests passed; adversarial review then found unsafe rollback and path-revalidation assumptions in the temporary helper. Dedicated failing regressions preceded those fixes. The final operational suite passed 32 tests across quarantine, archives, pruning, supplements, and standalone restoration. No rollback was invoked during the live operation. After isolating the separate startup-panic generation, all 22 referenced collections became green and three real sparse queries succeeded. Full backup restoration verified 13,331 files and 11,763,626,499 bytes against original SHA-256 hashes. Pruning completed with 19 exact targets recorded in its synchronized journal; both archives and tested recovery instructions were retained.
- **Prevention/follow-up:** Keep retired metadata outside the active reference namespace after explicit identity verification. Distinguish startup failure from GC failure, file lengths from disk allocation, and reversible quarantine from reclaimed space. Full recovery, disk reclamation, and installed hybrid-search/daemon health are separate gates.
  Final measurement with the same allocation accounting: 34,976,563,200 bytes before recovery versus 22,382,116,864 bytes afterward, including the retained backup and incident quarantine; 12,594,446,336 bytes (11.73 GiB) reclaimed. Active Qdrant storage was 18.24 GiB, the recovery bundle 0.90 GiB, and the intact incident collection 1.70 GiB. All 22 manifest hashes were unchanged. The unmodified final GC dry-run retained 23 collections with zero deletion candidates or errors. No Qdrant/index writer remained, and the indexing service was still stopped; full installed hybrid-search health remains unproven.
- **Reusable learning:** Fail-closed GC can be operationally correct yet permanently blocked by an old metadata format. Repair the proven-obsolete metadata state; do not make collection deletion less conservative.
