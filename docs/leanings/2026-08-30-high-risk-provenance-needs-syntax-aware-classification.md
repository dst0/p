# 2026-08-30 — High-risk provenance needs syntax-aware classification

- **Status:** Resolved
- **Task/context:** Restore agent liveness after post-implementation requirement definition began classifying recovery test workflow as a product invariant, while retaining fail-closed coverage for real security, integrity, and state guarantees.
- **Unexpected observation or failure:** A workflow that ran a focused recovery test was marked high-risk because risk detection searched words inside command selectors. Live installed AI-units exposed the same class in passive acceptance wording: `npm test is run as a recovery fallback`, `npm test is used as the recovery fallback to run tests`, and finally `npm test is run as recovery to execute tests` retained `recovery` and triggered focused invariant evidence even though they only described test-command selection. The last form locked an accepted requirement batch into an impossible focused-proof loop because the task also forbade test-file changes. Adversarial review then found that punctuation-free `if … then …` wording remained falsely high-risk, while masking `Use npm test as a recovery fallback without partial mutation` also hid a real state invariant. Preserving the condition fixed the latter but still leaked procedural names such as `test:recovery` and `the recovery test`; later determiner, passive-selection, leading comma/colon/no-punctuation variants, reversed `fallback for recovery` order, and test-purpose wording leaked labels such as `recovery tests` and `manifest tests`. After the original false positive was removed, direct prompts exposed two opposite structural errors: `Security:` was treated as an uncovered invariant, while a normative Markdown heading such as `## Unauthenticated requests must be rejected` was skipped entirely. Opposite polarity in requirement text and acceptance criterion then cancelled after concatenation, and semantically overlapping logging requirements could omit rejection or an authentication prerequisite without reversing either one.
- **Evidence:** Regressions demonstrate that parsed test selectors, active, passive, conditional, determiner, command-selection, and explicit test-purpose recovery-fallback wording, quoted or unquoted unavailable verification-command subjects, selector option/value pairs, and high-risk script names remain procedural. Compound shell commands, unrecognized conditional semantics, and residual invariant prose after test-purpose spans—such as `without partial mutation`, `while preserving state`, or `with authorization required`—remain high-risk. Direct-source regressions cover unrelated decoys, independent text/criterion polarity, omitted and dual-sided behaviors, explicit access prerequisites, newline-separated and compound invariants, standalone colon and Markdown headings, and normative same-line or Markdown-heading invariants. The complete family passes 114 files and 1,030 tests.
- **Approaches tried:**
  - **Attempt:** Classify risk from broad word matches over the complete workflow command.
    - **Outcome:** Did not work
    - **Why:** Selector names legitimately describe the invariant being tested without asserting that invariant as workflow behavior.
  - **Attempt:** Suppress every line shaped like a heading.
    - **Outcome:** Did not work
    - **Why:** Markdown can carry an actual normative user requirement, so unconditional structural suppression creates a provenance bypass.
  - **Attempt:** Concatenate requirement text and acceptance criterion before checking polarity.
    - **Outcome:** Did not work
    - **Why:** Opposite statements set both polarity flags and neutralize the exclusive conflict check.
  - **Attempt:** Reject only opposite polarity without requiring an agreeing source behavior.
    - **Outcome:** Did not work
    - **Why:** A related logging statement could retain subject words while omitting rejection, acceptance, preservation, removal, or a standalone prerequisite.
  - **Attempt:** Parse command structure and source structure first, then apply risk and semantic coverage to the remaining normative prose.
    - **Outcome:** Worked
    - **Why:** Syntax supplies the boundary between procedure, structure, and asserted behavior while preserving fail-closed residuals.
- **Root cause:** Lexical risk detection ran before structural classification, conflating command metadata, active, passive, conditional, and command-selection grammar, test-purpose labels, and headings with product/runtime assertions and then overcorrecting by trusting markup unconditionally. The fallback masker also had no representation for retaining a leading condition while replacing only its command, accepted too narrow a determiner and passive-verb vocabulary, required the noun `fallback`, recognized only `to run` purpose wording, and did not bound explicit test-purpose tails. Runtime-state detection omitted the common phrase `without partial mutation`. Polarity validation aggregated semantically distinct fields before checking each relevant assertion and treated agreement as optional.
- **Resolution:** Procedural masking now recognizes fully parsed focused test invocations, normalizes active or passive test-command grammar around both `recovery` and `recovery fallback`, accepts bounded `a`/`the`, reversed fallback order, punctuation variants, and passive selection forms, and removes only explicit `to run … test(s)`, `to execute … test(s)`, or `for … test(s)` purpose spans. It retains leading `if`/`when … then` conditions and any text after the bounded purpose span for independent semantic analysis. Within a recognized availability condition, only a parsed verification-command or generic test subject is normalized; Markdown inline-code markers are removed only from the recognition copy, and unrecognized original condition text remains available to risk detection. Text after the first purpose-span test noun remains available to classify state and security residuals. Direct prompts retain physical-line and literal-aware clause boundaries; only non-normative structural headings are skipped, and every normative high-risk clause requires semantically related eligible provenance. Requirement text and acceptance criterion are polarity-checked independently, while clause-level coverage requires every concrete polarity side across related atomic mappings and requires an explicit prerequisite predicate only when no concrete pair exists.
- **Verification:** The focused procedural suite passes 82/82 after reproducing the exact installed-live failure and every adversarial punctuation, order, purpose-tail, and residual-semantics failure. The complete requirement-verification family passes 118 files and 1,047 tests; a newly installed live run remains required after this final grammar extension.
- **Prevention/follow-up:** Keep high-risk classification ordered as parse structure, isolate residual semantics, classify normative content, then validate provenance and polarity. Preserve regressions for both false positives and false negatives whenever a structural exception is added.
- **Reusable learning:** Never decide semantic risk from raw keywords when syntax can distinguish labels, selectors, procedure, and asserted behavior.
