# 2026-08-24 — Rejected-definition next actions must be controller-global

- **Status:** Resolved
- **Task/context:** Validating candidate `5.0.1-rc.10` with the event-sourced inventory definition canary after adding aggregate and cumulative sparse-repair cardinality limits.
- **Unexpected observation or failure:** The aggregate fan-out was correctly rejected without draft growth, but the model then submitted a new complete definition instead of the required bounded repair and expanded the draft from 30 to 53 requirements.
- **Evidence:** The canary recorded an initial 30-requirement rejected draft, rejected a 38-replacement repair before merge, and then accepted a fresh 53-requirement `define` attempt because the prescribed next action existed only in guidance. Review found equivalent bypasses through `prepare_definition`, `declare_task`, and `ready_to_finish`, all of which could erase or disrupt the active rejected draft. It also found three lifecycle hazards: a later workspace mutation left an obsolete draft blocking final verification, a repair deleting every requirement could gain fresh-definition authority without exhausting the lineage budget, and an oversized recovery prompt hid the active repair revision while instructing a controller-forbidden `define`.
- **Approaches tried:**
  - **Attempt:** Tell the model not to restart with `define` unless cumulative lineage growth is exhausted.
    - **Outcome:** Did not work
    - **Why:** The tool schema still exposed `define` and other state-changing actions as legal calls, so prompt compliance was the only enforcement boundary.
  - **Attempt:** Guard only `define` while a repairable draft exists.
    - **Outcome:** Partial
    - **Why:** Other requirement-audit and task-verification transitions could clear the draft or consume audit state, recreating the same bypass indirectly.
  - **Attempt:** Make the required next action a controller-global XOR over the active draft.
    - **Outcome:** Worked
    - **Why:** A repairable draft now permits only `repair_definition`; a lineage-exhausted, directly submitted empty, or unrenderably large recovery draft permits only one complete `define`; task-verification permits only read-only `status` until that transition rotates, clears, or is invalidated by a later workspace mutation.
- **Root cause:** `next_required_action` was advisory and local to the prompt rather than a state-machine invariant. The active draft carried no controller-recognized authority describing which transition was legal.
- **Resolution:** Exact rejected-draft identity now carries a reasoned ephemeral fresh-definition authorization after cumulative lineage overflow, a directly submitted empty rejected batch, or recovery payload overflow when the complete authoritative source catalog still fits. The requirement-audit tool rejects every action except the authorized one, task-verification rejects every action except `status`, zero-result repairs fail before application, later workspace mutation invalidates the obsolete draft, and successful or rejected definition application consumes authorization by rotating to a new draft object. Oversized recovery keeps the active marker, revision, required action, and complete authoritative source while omitting only the unrenderable rejected batch.
- **Verification:** Regression-first tests proved the fresh-define, prepare, redeclaration, ready-to-finish, empty-draft, zero-result-repair, post-mutation, and oversized-recovery failures before the final guards. Focused suites cover prompt ceilings, reason preservation, controller acceptance of the instructed full definition, and fail-closed authoritative-source overflow.
- **Prevention/follow-up:** Whenever a controller emits a normative next-action marker, audit every tool and lifecycle path that can alter, clear, or rotate the governed state. Keep authorization tied to exact ephemeral state identity and consume it only through the intended transition.
- **Reusable learning:** A required next action is not real unless all sibling state transitions enforce it; prompt wording and one guarded tool action cannot protect a multi-tool state machine.
