# 2026-09-23 — source_output_paths authorization gate ran before the authoritative-source check

- **Status:** Resolved
- **Task/context:** A live benchmark ("Fix the bug in sub (it adds instead of subtracting)." against a local Qwen 27B model) stalled in STRICT/evidence verification mode. The model called `record_task_verification` with `source_output_paths: ["src/math.ts"]`, even though `src/math.ts` had never been selected as an authoritative requirement source for the task.
- **Unexpected observation or failure:** `declareCriticalProofSourceOutputs` (`packages/coding-agent/src/core/task-verification/taskverificationcontroller-methods/critical-proof-source-output.ts`) checked whether the current direct user prompt authorized mutating the path (via a standalone `[source-output:...]` marker) *before* checking whether the path was even an active authoritative source selection. Since `src/math.ts` was never selected, no marker could exist, so the call returned "Mutating authoritative source src/math.ts requires explicit user authorization... Ask the user to reply with this standalone line: [source-output:src/math.ts]". The model then had to ask the user for a marker that made no sense for an ordinary edit target, stalling the run.
- **Evidence:** Regression tests added in this change:
  - `packages/coding-agent/test/task-verification-source-output-non-authoritative.test.ts` — unit-level reproduction against `recordCompletionChecklist`/`declareCriticalProofSourceOutputs` directly.
  - `packages/coding-agent/test/suite/task-verification-non-authoritative-source-output.test.ts` — full `harness.ts` + faux-provider run of the exact "Fix the bug in sub" flow; confirmed to fail with the authorization-demand text before the fix (verified by temporarily reverting the source fix and re-running), and to pass afterward.
- **Approaches tried:**
  - **Attempt:** Keep the authorization check first, and instead relax the *content* of the message for unauthorized-but-unselected paths.
    - **Outcome:** Did not pursue
    - **Why:** The call site (`recordCompletionChecklist` in `completion-checklist.ts`) treats any non-empty return from `declareCriticalProofSourceOutputs` as a hard rejection of the whole checklist call — there was no way to keep it "blocking" without reproducing the same stall, just with different wording.
  - **Attempt:** Reorder the checks so authoritative-source-selection membership is decided first, and silently drop (ignore) any `source_output_paths` entries that are not an active authoritative source selection, rather than erroring.
    - **Outcome:** Worked
    - **Why:** Ordinary edit targets never need mutation authorization in the first place; only entries that survive the authoritative-source filter go through the existing marker/authorization logic, which is unchanged for real authoritative sources.
- **Root cause:** The unauthorized-marker check and the "is this path even an authoritative source" check were both blocking, but ran in the wrong order — the stricter (authorization) gate ran first, so it fired for paths that should never have been gated at all.
- **Resolution:** In `declareCriticalProofSourceOutputs`, compute the `criticalProofSourceSelections` membership set first and filter `source_output_paths` down to only the paths that are an active authoritative source selection before running the authorization-marker check. Paths that are not selected are simply ignored (no error, no authorization demand, no state written for them). A new `nonAuthoritativeSourceOutputNote` helper surfaces a benign, non-blocking note ("X is not an authoritative requirement source; omit source_output_paths for it and edit it normally.") appended to the checklist-recorded success message in `completion-checklist.ts`, so the model learns not to keep passing it, without blocking progress. The authorization requirement for genuine authoritative sources is unchanged.
- **Verification:** `npm run check` (biome, file-structure, pinned-deps, ts-imports, shrinkwrap, tsgo, browser-smoke) passes. All 98 `packages/coding-agent/test/task-verification*.test.ts` files (1062 tests) pass. The two new regression files above pass; the unit-level one was confirmed to fail against the pre-fix code and pass against the fix.
- **Prevention/follow-up:** Considered (per task instructions) hiding `source_output_paths` from the `record_task_verification` tool schema unless an authoritative source is already selected, to stop the model from offering it at all in the common case. Not done: `EvidenceVerificationSchema` (`packages/coding-agent/src/core/task-verification/constants.ts`) is a single static TypeBox schema shared by `createTaskVerificationToolDefinition`, built once per session/mode rather than per call, so making it depend on live per-call authoritative-source-selection state is not a one-line change; it would need the tool definition to be rebuilt (or a two-schema branch threaded through) each time selections change. Left as a follow-up if a maintainer wants to pursue it.
- **Reusable learning:** When a value can independently fail two different gates (here: "not authorized" vs. "not an eligible target at all"), check *eligibility* first. An ineligible input should usually be a no-op/ignore, not routed through a stricter gate meant for eligible-but-unauthorized inputs — the stricter gate's remediation instructions (e.g., "ask the user for X") can be actively wrong/confusing when the input was never eligible in the first place.
